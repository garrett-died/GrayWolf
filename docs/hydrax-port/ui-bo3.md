# UI: full map, prefabs and the BO3 conversion from the GUI

Branch `hydrax-parity`, based on 88aef3a; staged, not committed. Labels: **proven** (a check that fails when the code is reverted), **tested** (run, matches), **hypothesis**, **unknown**. Runs are under `GrayWolf-testrun\ui-bo3`. No Radiant, APE, cod2map, linker or game was run. The real BO3 install was never written to and `--target modtools` was never run against it: every Mod Tools write was into a fake root made of one empty `bin\linker_modtools.exe`, deleted after the gates. Nothing read `D:`.

## What changed

- **One shared conversion step** (`DiskGame.Bo3.cpp` / `.h`, new). The command line and the Load Game panel both call it, no second copy: `ReadPublish` (was `DiskGame.Cli.cpp` `ReadPublish`), `Begin` (the Touches refusal, `Preflight`, `ClearRunReports`), `Force` (the material GDT / full map / TIFF / XMODEL_BIN forcing that was at `DiskGame.Cli.cpp` 349-357), `Finish` (the publish step and the static gate that was the `Publishing` lambda), and for a GUI-shaped run `FromSettings`, `Prepare`, `Complete`. `DiskGame.Cli.cpp` now calls `FromCli`, `ReadPublish`, `Begin`, `Force`, `Finish` (lines 138-188); its own copies are gone.
- **Three settings** (`DiskGame.cpp` 135-143, `DiskGame.h`): `full_map` (off / on), `map_prefabs` (none / all), `bo3_convert` (off / `folder` "BO3 folder (inside the export folder)" / `modtools` "Into the Mod Tools (BO3 root)"). Common settings, so they show for the games whose readers export Map (full map, prefabs) or Model and Map (conversion), on the Settings page under "A game's own choices" (`ImGuiShell.Settings.cpp`; there is no other place the panel lists a game's settings). Help text in `DiskSettingHelp` (`ImGuiShell.Settings.cpp` 250-262): plain words, says a full PNG/TIFF map can take 10 to 20 GB and the run stops under 8 GB free. `map_prefabs` offers none / all only; the per-part list stays command line only (`--map-prefabs`), and the help says so. The settings self-test passes (it requires help for every setting). Any stored `bo3_convert` that is not `folder` or `modtools` reads as off.
- **The GUI run** (`ImGuiLoadGamePanel.Disk.cpp`): `StartExport` decides the conversion from the settings and the output folder (`FromSettings`); `DoDiskExport` runs `Prepare`, the export, `Complete`. The result banner shows where it was written, the verify verdict, failures and warnings, the number of `.bak` files, and buttons "Open the BO3 folder" and "Open the check report". With the conversion off the path is the old one (only `Force` takes `full_map` out of the options, so the setting cannot start a full-map write without a target).
- **Free space floor.** A converting GUI run sets the same 8 GB floor the CLI sets (the CLI's `--min-free-gb` has no GUI field), writes its floor row beside the reports, and gives the floor back after the run (`Prepare` / `Complete`).
- **Owner decision 2026-11-08, Mod Tools from the GUI.**
  - `FindModToolsRoot`: the Mod Tools folder setting, then the BO3 install found in the Steam libraries, then `TA_TOOLS_PATH`.
  - **Automatic switch**: when the output folder is in (or holds) a Mod Tools install (`Bo3Target::Output::Touches`), the run is the Mod Tools target on that install whatever `bo3_convert` says, and the raw staging export goes to `%TEMP%\GrayWolf-bo3-staging\<game>`, not into the root. The raw layout (`<game>\maps`, `models`, `images`) is never written into a Mod Tools root by a GUI run.
  - **Confirmation**: `Finish` first runs the plan (a run of the publish step that writes only the run's reports), then asks (`Hooks::Confirm`): the root, files to create / replace, GDT files to merge into, GDT backups (an old GDT that does not parse), and the gdt.db clash counts. The panel shows it as a modal (`DrawBo3Ask`, `AskBo3`), asked every time, no "don't ask again". No means nothing is written there. The CLI passes no hook and still needs `--mod-tools-root` for `--target modtools`.
  - The write itself is `--target modtools`'s own code: preflight, the manifest, merge mode, never over a file GrayWolf did not write, `.bak` before an unreadable GDT is replaced.
- **ZonekitZone.cpp `LoadBytes`**: a file named `*.zone` whose magic no container reader knows is read as a raw decompressed zone (what `zone-decompress` and the walk tools keep). Needed so the brief's `mwr\zones\mp_crash.zone` can be exported without the `D:` install. Any other file goes through `FastFile::Decompress` as before.
- **Test command** `gui-export-check` (`DiskGame.Bo3.Check.cpp`, new): the panel's export without the window: settings map as `DiskOptions` builds it (every setting at its default, then `--gui-setting key=value`), the same `FromSettings` / `Prepare` / `Export` / `Complete`, the confirmation answered by `--gui-answer`. It never looks for a Mod Tools root itself: only `--gui-mod-tools-root`.
- `DiskGame.h` includes `<mutex>` (it used `std::mutex` without it; the safety gate could not parse `CliCommands.Misc.cpp` once my header was included early).
- `ui-shot`: a step key `settings_game` (`ImGuiShell.Record.cpp`, `ImGuiShell.Settings.cpp`) shows a given game on the settings page; `tools/ui-shots/settings.json` has the step `settings-games-mwr`.

## Follow-up (coordinator, 2026-11-08): staging cleanup, automatic Radiant map, two-drive floor

- **Staging cleanup** (`DiskGame.Bo3.cpp`: `NewStagingFolder`, `RemoveStaging`, `RemoveStaleStaging`, `Prepare`, `Abandon`, `Complete`). The staging folder of an automatic run is `%TEMP%\GrayWolf-bo3-staging-<process id>-<tick>`, made by `Prepare` with a marker file `.graywolf-staging` holding the process id. It is removed after a successful publish, after No, after Cancel, after a failure and after a refused start, and `RemoveStaging` only removes a folder that has that name prefix and the marker (and is no install). A failed removal is logged and shown in the result banner ("Could not remove the temporary export"). The gate report, which lived in the staging folder, is first copied with the placement and approximations reports to `%TEMP%\GrayWolf-bo3-last-check` (overwritten each run) so "Open the check report" still works. At GUI start (`LoadGamePanel` constructor) `RemoveStaleStaging` removes folders of that name and marker whose process is no longer running; other processes' folders (the owner's open windows), folders without the marker and any other name stay. **proven** by the self-test (a dead process's folder removed; a live one, a lookalike without the marker and another folder kept; a non-staging folder refused). **tested** by `gui-export-check` runs on a fake root (below).
- **Automatic Radiant map.** `Force` now also sets `map_radiant` on when a target is set and the run exports maps (`C.Kinds` has Map), like `material_gdt`. This is in the shared function, so a CLI run with `--target` and a map but without `--map-radiant` now also writes the Radiant `.map` (before it did not). A CLI run that already says `--map-radiant on` is unchanged (the parity runs above used it). The help text of the three settings no longer asks the user to tick it. **proven** by the self-test (forced with maps, not forced with models only, not forced without a target).
- **Free space on both drives.** `Prepare` checks the drive of the export (the staging folder for an automatic run) and the drive of the target (the Mod Tools or BO3 folder) against the floor (8 GB, or what is set) and refuses the run with the drive named: "The drive C: has only 2.8 GB free, under the 8 GB that stays free ... It holds the staging export." The CLI path is not changed (its own floor behaviour stays). **tested** with `GRAYWOLF_TEST_FREE_BYTES` (the test hook of the floor): the refusal named C:, the staging folder made for the run was removed, and a stale staging folder placed in the parent was removed first. **unknown**: a run where the two drives differ (the hook gives both the same free space).
- Fake-root runs again, results: **tested** (`keep\logs\gui_G_floor.txt`, `gui_H_no.txt`, `gui_H_yes.txt`): with a stale staging folder (dead process id), a lookalike without the marker and an unrelated folder in the staging parent, the floor refusal removed only the stale one. The No run (with `bo3_convert=folder` and the output in the fake root, so automatic) left the fake root byte for byte as before and no staging folder; the Yes run wrote 755 files into the fake root, including `map_source\graywolf_maps\mp_crash.map` although `map_radiant` was never set (forced by the conversion), ran the gate and left no staging folder; the lookalike and the unrelated folder stayed. Dev and DevAsan self-tests pass, safety gate clean, BO4 hash 3034125e...428f238e unchanged. The fake root, staging parents and exports are deleted.

## Follow-up 2 (review fixes)

- **Shutdown hang.** `~LoadGamePanel` sets `DiskCancel` and wakes the question (`Bo3Q.Wake()`) before joining the worker. The wait is a `DiskGame::Bo3::Question` (a condition variable, 100 ms timeout, Cancel is No). **proven** (self-test: a cancel ends a waiting `Ask` with false inside 5 s; an answer returns Yes).
- **Junctions and symlinks.** `Begin` now also checks the folder the run writes (`<out>/<game>`) with `Touches` (which resolves junctions and symlinks through `weakly_canonical`), and `Prepare` re-judges `<out>/<game>`: one that resolves into an install turns the run into the Mod Tools target with a staging export. **proven** (self-test with `mklink /J` junctions made inside the test's own folder and removed with `RemoveDirectoryW`): `Touches` and `IsUnder` follow a junction into an install; an output that is a junction is automatic; `Begin` refuses a run folder that is a junction into an install; the junction's target is intact after removal. **tested**: a `gui-export-check` run with `--out` a folder whose `mwr` is a junction to the fake root went the Mod Tools way (below).
- **Question from any page.** `DrawBo3Ask` is called from the shell's frame (`ImGuiShell.cpp`), not `DrawExportBar`, and the popup follows the question: when it ends the popup closes on the next frame. **tested** with `ui-shot` (`tools/ui-shots/bo3-ask.json`, step keys `ask_test` / `ask_drop` on the `loadgame` step, a test hook with no worker behind it): the modal shows over the Settings page and over the Library page, and is gone after the drop (the cancel path). The wait ending by Cancel in a real run was tested only through the `Question` self-test.
- **Staging deletes.** The marker is written to a temporary file and renamed. An empty or unreadable marker, process 0, or a failed `OpenProcess` (access denied) counts as live; only `ERROR_INVALID_PARAMETER` is gone. A staging entry that is a junction or symlink is skipped and `RemoveStaging` refuses it (never `remove_all` through one). If the marker cannot be written, `Prepare` removes the folder it just made, by its exact path. **proven** by the self-test (empty, zero and text markers stay; a gone process's folder goes; a junction named like a staging folder is not followed, its target keeps its files; a process that cannot be opened is not gone). The marker-write failure path has no test of its own (**unknown**).
- **Self-test folder.** `graywolf-bo3run-selftest-<pid>-<tick>`, made with `create_directory` (a name taken fails the test), and only that folder is removed.
- **full_map parity.** `Force` no longer erases `full_map`: only `--full-map` (or the GUI request) sets it, nothing removes it, as before my change. The reason for the erase was the panel: it keeps `full_map` as a setting that is always in its options, and `FullMapOn` reads that key, so with the conversion off a saved "on" would have written the full-map files with no target. That erase now lives in `Prepare` (the panel-shaped path, never the CLI): `if (!Converting) O.Settings.erase("full_map")`. **proven** by the self-test (`Force` with no target leaves a saved `full_map` alone).
- **Left as listed.** `Finish` without a `Confirm` hook is the CLI's path (its `--mod-tools-root` is the consent): commented in `DiskGame.Bo3.h`; `Complete` (the panel-shaped path) refuses a modtools target with no hook ("internal: ..."), nothing is written. `LoadBytes`: the extension match is case-insensitive and a file whose magic has "ff" in bytes 2 and 3 (a fast file, even a damaged one) is refused the raw fallback.

## Follow-up 3 (second review)

- **Every GUI run with a target stages.** `FromSettings` now gives a run with `folder` or `modtools` a staging folder of its own (new, so it holds no junction); the raw export is written there and only the conversion's output reaches the target. The folder target still ends in the export folder the user chose: `Request::FolderOutputBase` makes `ReadPublish` put it at `<export folder>\<game>\bo3`. Because the raw export is removed, the banner points at the BO3 folder (or the export folder), the "Open export log" button is hidden for such a run, and nothing is merged into the Library list from a staging folder. A run with no target still writes raw files into the export folder as before.
- **Links already under the run folder.** `CheckRunFolder` (`DiskGame.Bo3.cpp`) scans the directories that exist under the run folder, and under the folder target's own folder, directories only, never entering a link. A junction or symlink whose real place is in a Mod Tools install (`Touches`) or in the game install (`O.Install`) refuses the run before anything is written, and the message names the link. It runs for every run: the CLI (`DiskGame.Cli.cpp`, any target, none included) and the panel (`Prepare`, before anything else is decided, so a link inside `<out>\<game>` is refused and not turned into a write through it; `FromSettings` also refuses an install found as a link inside the export folder). **proven** (self-test, nested `mklink /J` made inside the test's folder: `images` into an install is refused with the link named, `models` into the game install is refused, a link to a plain folder passes, one under the folder target's own folder is refused, the run passes again once the link is gone; the junctions are removed with `RemoveDirectoryW`). **tested** (`gui-export-check`, `<out>\mwr\images` a junction to the fake root): `bo3_convert` off is refused with the link named and nothing written to the fake root; a `folder` or `modtools` choice, whose raw export is in a fresh staging folder, runs and never writes through the link.
- **Marker failure.** `MakeStaging` makes the folder and its marker and, when the marker fails, removes the folder it just made by its exact path (the `.tmp` goes with it), after checking the staging name and that it is no junction or symlink; `Prepare` no longer goes through `RemoveStaging` (which needs the marker) for this. **proven** (self-test with `MarkerFailureForTest()`: the folder and its `.tmp` are gone; a folder without the staging name is left; an existing folder or a junction at that name is not taken over; a good call leaves the marker and no `.tmp`).
- **Truncated fast file.** `RawZoneRefusal` (`ZonekitZone.cpp`) reads the first bytes itself: a file shorter than 4 bytes, or one with "ff" in bytes 2 and 3, is never read as a raw zone, whatever its length or damage; `LoadBytes` reads only what it passes. **proven** (self-test: `IWffu100...`, `IWff` and `TAf` refused, an empty file refused, other first bytes accepted).
- **Tested gates.** Dev and DevAsan builds, all self-tests on both, safety gate clean, BO4 hash 3034125e...428f238e. `mp_crash` geometry-only `--target none` from `mwr\zones\mp_crash.zone`: 763 files SHA-256 identical between a tip build with only the first `LoadBytes` patch and this change (run before the last `Prepare` edit, which the CLI does not call). Fake-root Yes, No and folder-target runs: see the logs in `keep\logs` (`gui_L_*`). Fake roots and junctions are deleted.
